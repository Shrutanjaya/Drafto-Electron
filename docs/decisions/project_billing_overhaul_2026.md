Started 2026-08-03. Goal: enforce subscriptions, sell document types by court, monitor accounts. Supersedes nothing; see [[project_entitlement_enforcement]] for the app-side layer and [[reference_drafto_subscription_stack]] for the service map.

**THE DECISIVE CONSTRAINT (verified 2026-08-03, live data):** every paying customer is on **UPI Autopay**, and each mandate's ceiling equals *exactly* the plan price — 4 × ₹499, 1 × ₹999 (Gauraan, Chamber). Zero headroom. Razorpay's subscription-create API exposes **no parameter to register a higher ceiling** (only plan/quantity/start/addons/offers). Therefore **any price rise or costlier plan requires the customer to re-approve autopay in their bank app.** Adding *features at the same price* needs nothing. Read the cap via `GET /v1/payments/{id}?expand[]=token` → `token.recurring_details.amount_blocked` (the CLI has no token command).

**PLAN DESIGN (user-decided; prices CONFIRMED 2026-08-03):** replace Solo/Chamber/Enterprise with **Niche ₹999 / Dual ₹1999 / Max ₹2999**, effective 15 Aug 2026 when Early Bird ends. **Plans sell HOW MANY fora, not WHICH** — Niche = any 1 court of the customer's choosing, Dual = any 2, Max = all incl. future (user's call 2026-08-03: forcing SC on a CAT-only practitioner would lose that customer). So still only 3 Razorpay plans: the plan sets the allowance, the user's record (`courts: Forum[]`) holds the selection, captured at checkout via subscription `notes`. Selection is **per forum, not per document type** (replies/rejoinders arrive with the forum they belong to). **Swap policy: one change per billing period** — what's actually sold is *simultaneity*, so a Niche user can rotate but never hold two fora at once; anyone needing two concurrently must buy Dual. Swapping doesn't change price → **no mandate re-auth needed** (only upgrading does). Consequence: the locked-doctype prompt has two forms — "Add this court" (free, plan has an unspent slot) vs "Upgrade to access" (costs more). NOTE: seats are a plain Razorpay `quantity` multiplier with **no volume discount** (user declined) → a 3-seat Niche chamber pays 3×₹999=₹2,997 vs ₹999 for old Chamber/3 devices. Only Gauraan is multi-seat and he's grandfathered a year. Device count is **dropped as a plan axis** — seats become Razorpay `quantity` (coverage × seats, independent). Device gating/manage-devices in the app is KEPT; only the source of the seat number changes (was plan name → becomes subscription quantity). Razorpay plans are immutable → 3 new plans, old ones retired but existing subs stay on them.

**GRANDFATHERING (user-decided, "let the coverage expire, not the price"):** the 5 existing payers get full-suite access until **15 Aug 2027** at their current price, then silently drop to SC-only unless they buy a current plan. Autonomous by design — it's a date on each user record checked at every entitlement resolution, so no cron, no manual step at the deadline. One-time **in-app consent screen** (not email) records acceptance + timestamp + exact wording shown; a confirmation email follows automatically. Offer must be accepted by **15 Aug 2026**; if not accepted they simply stay SC-only (nothing removed). A reminder email goes out 30 days before the 2027 cliff. Consent copy: user drafted it, corrections applied 2026-08-03 — price must be **per-customer** (Gauraan is ₹999, not ₹499), CAT covers **all 17 regular + 13 circuit benches** (not just Principal Bench), acceptance deadline stated, future tense before the Accept button.

**SECURITY FIX 2026-08-03 (deployed, commit ee1f795):** `firestore.rules` had `match /users/{userId} { allow write: if isOwner(userId) }` — i.e. **any signed-in user could set their own `subscriptionStatus`/`plan`/`deviceLimit`/`accessOverride`/`suiteAccessUntil`**, which is the exact doc the app reads for entitlement. Proven exploitable against production (minted a custom token for a throwaway uid via the SA key → Identity Toolkit `signInWithCustomToken` with the public web API key → Firestore REST PATCH succeeded). Would have silently defeated Phase C. Fixed by restricting create/update to `hasOnly(['email','displayName','createdAt'])` (the only fields the client writes — auth-service.ts signUp/signInWithGoogleCredential/updateDisplayName) and denying delete. Re-probe after deploy: 8/8. Reusable probe at `~/drafto-ops/rules-probe.mjs`. **`usage/{uid}` and `sessions/{uid}` are still client-writable** — usage counters can be faked (cosmetic, but it's Phase E dashboard data); sessions must stay writable for device management (no escalation).

**POST-2027 TERMS — RECONFIRMED 2026-08-04 (was misunderstood once, don't re-litigate):** after 15 Aug 2027 the grandfathered customers **keep paying ₹499 (Gauraan ₹999) and keep Supreme Court drafting indefinitely**. They lose ONLY the High Court and CAT. They are **not** required to move to Niche/Dual/Max — that is optional, and only to regain the extra courts. The user briefly thought they'd be pushed onto ₹999 for SC too; they will not. Two independent reasons: (a) it is the design he chose ("let the coverage expire, not the price"), and (b) **it is unenforceable anyway** — each UPI mandate is capped at exactly their current price, so no rise is possible without their re-approval. The only way to force it would be cancelling their subscription and making them re-subscribe. Accepted consent wording says price "will not change during this period" and coverage "will return to Supreme Court work only, unless you move to a current plan" — so post-2027 price is left open, but coverage-narrowing is a firm commitment.

**OPEN / UNFIXED:** (1) **Repeat free trials** — nothing stops a new 7-day trial from a fresh email; a real customer did exactly this on 2026-08-04. Phone is not a reliable dedupe key (his two signups differed by one digit, a typo). Standard fix: at checkout, if the email has had a trial, create with no trial and charge immediately. (2) **Separate last-DOCX / last-PDF timestamps** for the admin dashboard — only a combined "last generated" exists; needs an app change and will have no history before that release.

**PHASES:** A stop the leaks (webhook) · B rebuild /account (self-serve renew/cancel/upgrade + real status) · C switch enforcement on · D court-coverage plans + upgrade flow · E admin dashboard. B is the shared dependency for C, D and E — it needs the site's first authenticated API surface (no Firebase Admin credential exists on Vercel today; all 3 current routes are unauthenticated).

**Why:** ~₹2.5k MRR, 4 paying subs; the app enforced nothing, so cancelled users kept full access. **How to apply:** never let anything but a Razorpay payment event set a user to active — the user is emphatic that visiting the account page must never activate an account.
